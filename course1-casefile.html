A sample from the case file

Book 1 — The Access List

SoD conflict testing · Intermediate, session 2 · taught live on S/4HANA and GRC Access Control.

1 · The situation

Pull the current Segregation of Duties (SoD) conflict report for Accounts Payable and confirm whether vendor master maintenance and payment run execution sit on the same user ID.

2 · What proves it

A dated export of the Access Risk Analysis report, the specific role names and authorization objects in conflict, and — if one is claimed — the mitigating control ID with its last review date.

3 · The trap

Running Access Risk Analysis at the role level instead of the user level can hide a real conflict when two separate, individually clean roles combine only when assigned to the same person. Always confirm at the user level.

4 · Demo Lab
  1. Run Access Risk Analysis for the vendor-master + payment-run risk at user level for the Accounts Payable unit.
  2. Export the results — that is your population of flagged users.
  3. In PFCG (display only), confirm which roles actually carry both authorization objects.
  4. Cross-check role assignment history in SUIM, in case a role changed recently.
  5. If a mitigating control is claimed, pull its Mitigation ID and its last review date.
5 · Defend It

Reviewer challenge: “Did you confirm the conflict at user level, or only trust the role-level report? What mitigating control exists, and when was it last reviewed?”

Answer it yourself first — then reveal the model answer

A role-level run can show two roles as individually clean while one person holds both, so the conflict is confirmed per user — from the user-level Access Risk Analysis export, cross-checked in PFCG and SUIM. A mitigating control counts only with its Mitigation ID and a dated record of its last review; “it's mitigated” without that evidence is a claim, not a control.

Why this isn't a manual

Most SAP training teaches you where the buttons are. This teaches you what to look for before you touch one.

Conventional trainingRun Access Risk Analysis. Export the report. No conflicts — done.

Correct, and not enough. It says nothing about whether the report could have missed the conflict, or what evidence an auditor will actually accept.

The method

Every live session runs on the same four beats.

Because this is the order an engagement forces on you — and rehearsing it every session is what makes it automatic on a client system.

Understand the control before the system

Hour 1: the scenario, the control objective, the trap it's built around, and what good evidence looks like.

Watch it done live

Hour 2: the instructor runs the real T-codes and Fiori apps on a live S/4HANA training client, display-only, as on a client system.

Do it yourself

You repeat the full walkthrough on your own login before the next class; your evidence is spot-checked at the start of it.

Defend it

The last 15 minutes: two students present their conclusions as if to an external auditor, and the instructor pushes back.

The thread through every Book

Every case ends by naming the pattern, not just the finding.

The test: would a failure actually show up in the evidence you're relying on? If not, you are holding the wrong evidence.

The same error — mistaking a control's documentation for evidence that it operated — comes back in a different disguise in Book after Book. Recognising the pattern is what lets you catch it on a system you've never seen.
